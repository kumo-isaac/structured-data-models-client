## T2.8

A ranking (`RANK TOP k`) on the core route is the core's from the question to the answer, as E153 made a forecast's split the core's: the core splits it into one binary question per candidate, refuses what the reference refuses, gathers and asks each question, and puts the answers back together; the Python host passes `candidates` and `top_k` through and gives the result back as the caller's values.

### What changed

- **The contract (v26, optional fields, as T2.2's `key_dtype` and T2.18's `Materialized.query`)**: `Materialize.candidates`, a JSON list of contract scalars, each candidate of its own type (a missing one null, a value no scalar holds as its text), so a list mixing integers, floats and decimals keeps each its own, which an Arrow column would not; `top_k` among the call's values (`Materialize.values`), no longer a name-only option; `RequestState.ranking` (`top_k`, the first candidate's name, and each later question's candidate position, name, payload, query and request id); `Predicted.unscored_candidates` (positions); a ranking's result is the documented `rankings` (each candidate's JSON text, best first) and `scores` columns; the payload's task carries `top_k` where a plain question is asked with it, as the engine writes it.
  The schema, the state payload's schema and the lock entry are regenerated by their generators.
- **`sdm-request`'s `ranking`**: the candidates read from their scalars and kept once as `dict.fromkeys` keeps them (a number by its exact value whatever its type, so `1`, `1.0`, `True` and `Decimal('1.00')` are one); each written as `_as_literal` writes it by the ranked column's dtype, with its refusals by rule (`candidate_missing`, `candidate_bool`, `candidate_not_exact`, `candidate_not_whole`, `candidate_unwritable`); each question written as `_per_candidate` writes it, the table quoted where a bare name cannot spell it; the answers put back together as `_ranked` does: one row per row and entity asked about, each candidate scored by its positive class's probability (`true`, `True`, `TRUE`, `1`), sorted best first with ties in the order asked and a NaN last (PD-1), cut to `top_k`, and an answer without the probability refused `INTERNAL_ERROR`.
- **`sdm-core`**: the PQL adapter gives a ranking's plan (`RankingPlan`); `materialize` refuses in the client's order a statistic (`ranking_statistic`), a ranking over no aggregation (`ranking_column`) or over filtered rows (`ranking_filter`), no candidates (`candidates_missing`), none left (`candidates_empty`), more than the host's limit (`too_many_parts`, `most_parts`, now sent on every call), an open window (`open_window`), each candidate that cannot be written, and a `top_k` outside 1 to 20; candidates on a question that ranks nothing (`candidates_not_ranked`); the forecast's `top_k` read from the values; then gathers each question with a materializer of its own, a refusal naming its candidate (`ranking_candidate`, `ranking_parts`).
  `predict` refuses outputs a ranking does not give (`ranking_outputs`), checks every question as `_candidates_no_context_teaches` does, leaving out a candidate whose context holds one class (notice `CANDIDATES_UNSCORED`; all left out, `ranking_unscored`), asks each remaining question as a classification (`parts_answered` on a later failure), and reassembles.
  `top_k` on a plain question is read and written into the task (the not-yet rule `top_k` gone).
- **A target's row filter**: `COUNT(table.* WHERE table.column op constant, ...)`, the form every ranking question takes, is labelled as the reference's executor labels it (`execute_filter`, `execute_rel_op`: a float column at float32 with the constant cast to it, an integer column at float64 against a float, text against text, `NULL` equal to a missing value); every other filter is still refused `target_filter`, T2.10's.
- **Predict's not-yet rules lifted**: `response_field` for an item's `scores` and `rankings` (read as the bindings' `_float_tuple` and `_mapping_tuple`, laid out as `scores` and `rankings`); `prediction_type` (a class not of the target's type given back as written, the column typed as the reference's frame types it where the answers are of one kind, else with `prediction_as_answered`); `instance_id_type` (an instance id compared as the reference's `str` gives it for an integer, text, a float, a boolean and a null; a list or an object matches no id, with no Python repr written in the core, L0's vocabulary rule); a non-text `prediction_statistic` sent as the adapter's `_output_for` sends it.
  The census's probes of the four lifted rules are taken out (their sites gone), as T2.1a took out `target_type`'s.
- **The Python host**: on the core route every query goes to the core whole (`PredictiveQuery._on_the_core`, replacing `_in_steps_on_the_core` and `_on_the_core_alone`); `parts_of` is the old route's only; the core's refusals are said in the reference's words (`decompose.said_as_parts_are`, `client._said_of_the_part`); a ranking is kept as one request per question (`_kept_as_parts`) and predicted by the core (`_rust/predict.py`'s `_ranked`); `run` takes a per-run wording of a notice (`words`) so `CANDIDATES_UNSCORED` names candidates as given.
  Each change to frozen bridge code is declared in `bridge_changes.json` (E50).
- **The runners**: python-core's runner takes a ranking's question ids, passing over those of questions asked no call, and records list columns as the pure-Rust host does; rust-host passes `candidates` and `top_k` from the case's input and holds a ranking's state through `predict`.
  These are judging-path files (below).
- **Register**: P2D-1 (a candidate Python cannot hash written as its text, where the reference raises `TypeError`) and P2D-2 (an answer's `rankings` member of pairs whose first member is not text refused) proposed; PD-1's note (public calls cannot reach a NaN ranking score).
- **The gate's data for the new cases**: baselines (`ratchet.py accept --checkpoint f42d92ea`, only the twelve cases' lines taken) and L4 goldens on all three databases (24 DuckDB, 27 SQLite, 24 Postgres requests, from python-core's runs; rust-host's SQLite statements are among them); three refusal-map citations moved to their lines' new places.

### Probes

- A scenario sweep through the public calls, python-ref against python-core, 56 scenarios on DuckDB with an endpoint answering probabilities: the outcome, stage, class and code, the part queries, every request the endpoint received but its request id, `to_pandas()`, `.items`, `unscored_candidates` and the warnings' classes.
  All agree but one: a ranking whose entity clause has a filter, refused by the core's not-yet rule `entity_filter` (T2.13).
  Covered: integer, text, float, decimal, NumPy, `pd.Timestamp` and mixed candidates; repeated, missing, NaN, boolean, unwritable, too many and empty candidates; `top_k` as option, zero, 21, float, boolean and none; `RANK` without `TOP`; a `TOP 25` query; `CLASSIFY`; a statistic; a filtered target; candidates on a binary query; `top_k` on a regression, valid and not; `top_k` on a forecast; one and every candidate unscored; no probabilities; outputs `rankings`, `prediction`, `probabilities` and none; ties; an answer carrying `scores` and `rankings`; off-type classes.
- A ranking over a column whose name holds a dot (T2.18's carried P3): the core writes the questions with the name quoted and answers; the reference refuses the query, as KO2-36 registers for any such query (P2E-1).

### Deviations and questions

- The contract additions are v26 additions after T2.1b, as T2.2's and T2.18's were.
- The row filter of a ranking's questions is part of T2.10's `target_filter`, lifted here for the one form the questions need, since no ranking can be gathered without it.
- A difference not measured, only read: an endpoint answering an instance id equal to Python's repr of a list or object instance id is taken by the reference and refused by the core (`INVALID_RESPONSE`); no payload the core writes holds such an id.
- Judging-path files touched: `contract/runners/run_python.py` (a ranking's question ids, list cells); `rust/crates/sdm-testkit/src/host.rs` (protected: candidates, `top_k`, a ranking's state). The gate overlays the checkpoint's `run_python.py`, whose request-id check fails a ranking that reaches predict, so the runner change lands first, alone.
